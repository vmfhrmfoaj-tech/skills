# Understanding Doc

사람에게 결정을 묻거나 이해를 확인하기 전에, 그 사람이 먼저 읽을 **이해 문서**를 만든다. 설명은 문서가 맡고, 대화는 층마다의 링크와 질문만 맡는다.

문서로 옮기는 까닭: 대화창은 한 응답 길이에 묶여 큰 그림과 세부를 한 번에 못 보이고, 그림도 ASCII 로 좁아진다. 문서는 큰 흐름에서 세부로 내려가는 층을 층마다 한 파일로 두어, 사람이 이번 질문에 새로 필요한 층만 열고, 질문을 받은 뒤에도 다시 펼쳐 볼 수 있다.

## 언제 쓰나

- `decision-question` 과 `improve-understanding` 이 사람에게 묻기 전에 이 파일을 읽고 따른다.
- 사람이 설명 문서를 직접 청할 때 단독으로 쓴다. 단독이면 [읽을 곳](#대화에-주는-읽을-곳) 블록과 층마다 한 줄 요약을 알리고 끝낸다.

## 읽는 사람

**개발을 아는 1년차 주니어**로 가정한다.

- 안다고 봐도 되는 것: 함수·모듈·import, 파일과 폴더, JSON, HTTP 요청과 응답, git 기본, 단위 테스트, 리팩토링이라는 말.
- 모른다고 볼 것: 아키텍처 용어(seam, adapter, 의존 역전 등), 이 저장소에만 있는 이름(IR, 단계 이름, 도구 이름), 약어. 처음 나올 때 그 자리에서 괄호나 한 문장으로 풀어 준다.

설명은 개발 경험에 기대고, 식당·도서관 같은 생활 비유는 쓰지 않는다. 생활 비유는 비유와 실제를 다시 짝짓는 일을 하나 더 시켜서, 개발자에게는 오히려 이해를 흐린다.

## 입력

부르는 쪽(또는 사람)이 넘긴다.

| 입력 | 필수 | 설명 |
|---|---|---|
| 주제 | 예 | 무엇을 이해시킬지. 예: "주문 처리 흐름" |
| 근거 문서 경로들 | 예 | 설명의 출처. 없으면 주제에서 찾을 자리를 직접 찾는다 |
| 목적 | 예 | `결정`(결정 대상 한 줄을 함께) 또는 `학습`(이번에 배울 개념을 함께. 없으면 1층만) |
| 이해 문서 폴더 | 아니오 | 같은 주제로 이미 만든 폴더. 있으면 그 안의 층 파일을 다시 쓰고, 없는 것만 만든다 |

## 층마다 파일 하나

층을 파일로 나눈다. 한 파일에 1·2·3층을 다 담으면, 질문할 때마다 이미 본 1·2층을 다시 지나야 하고 이번 질문의 요지가 묻히며, 읽을 곳을 찾는 수고가 생긴다.

| 파일 | 담는 것 | 언제 만드나 |
|---|---|---|
| 1층 | 주제 전체 큰 흐름 | 주제당 처음 한 번 |
| 2층 | 단계 또는 개념 하나의 세부 흐름 | 이번 결정·학습에 필요한데 폴더에 아직 없을 때 |
| 3층 | 결정 하나에 걸린 규칙·지금 상태·문제 지점 | 목적이 결정이거나 질문이 특정 규칙·문제 지점에 걸릴 때, 질문마다 |

- **사람에게 링크를 준 파일은 고치지 않는다.** 사람이 앞서 연 링크의 내용이 바뀌면 헷갈리기 때문이다. 링크를 주기 전(같은 실행 안의 문법 검사 등)에는 고쳐도 된다.
- 고칠 곳이 생기면(코드가 바뀌었거나, 빠진 연결·헷갈리는 그림·틀린 줄을 찾았거나) 그 파일의 **새 판**을 만든다. 새 판 머리에 이전 판 링크를 적고, 그 뒤로는 새 판을 링크한다.
- 폴더에 있는 파일을 다시 쓰기 전에 머리의 기준 커밋과 지금 커밋을 비교한다. 그 파일이 인용한 코드 파일이 그사이 바뀌었으면(`git diff <기준 커밋> -- <파일들>`) 인용한 줄을 다시 확인하고, 어긋나면 새 판을 만든다.
- 파일 하나에는 그 층만 담는다. 다른 층의 내용을 옮겨 적지 않고 머리의 링크로 잇는다.

## 문서 자리

- 주제마다 폴더 하나를 이번 세션의 임시 폴더에 둔다. 환경이 세션 전용 임시 폴더(scratchpad 등)를 알려 주면 그 폴더를, 없으면 `${TMPDIR:-/tmp}` 를 쓴다. 폴더 이름은 `understanding/<YYYYMMDD-HHMM>-<주제를 줄인 영문 kebab>/`.
- 파일 이름:
  - 1층: `1-overview.md`
  - 2층: `2-<단계나 개념을 줄인 영문 kebab>.md` (예: `2-payment.md`)
  - 3층: `3-<결정 대상을 줄인 영문 kebab>.md` (예: `3-payment-error.md`)
  - 새 판: 이름 끝에 `.v2`, `.v3` (예: `2-payment.v2.md`)
- 저장소 안에는 만들지 않는다 — 사람이 요청하지 않은 파일이 작업 트리에 남기 때문이다. 사람이 다른 자리를 말하면 그 자리에 둔다.

## 준비

1. 근거 문서를 끝까지 읽는다. 문서가 가리키는 실제 코드도 연다. 문서와 코드가 다르면 코드가 사실이고, 그 차이도 문서에 적는다.
2. 근거 문서 곁의 진행 기록·결정 기록·인계 메모(예: `decisions.md`, `handoff.md`)도 읽는다. md 옆의 html 같은 생성본은 읽지 않는다. 근거 문서가 열린 문제로 적은 것이 이미 정해졌을 수 있고, 낡은 상태를 설명하면 사람의 시간을 버린다.
3. 실행 진입점에서 출발해 실제 호출 차례를 따라간다. 설계 문서의 그림만 옮기지 않는다.
4. 이해 문서 폴더를 받았으면 그 안의 파일 목록과 머리를 읽고, 이번에 다시 쓸 파일과 새로 만들 파일을 가른다. 이미 있는 층을 다시 조사하지 않는다.

## 파일 구조

모든 파일의 머리:

````markdown
# <층> — <풀어 쓴 이름>

- 대상: <저장소> · 기준 커밋 `<해시>` · <YYYY-MM-DD>
- 주제: <주제>
- 함께 보는 파일: [1-overview.md](</로 시작하는 절대 경로>) · [2-<…>.md](<…>)      (1층은 없음)
- 이전 판: [<파일 이름>](</로 시작하는 절대 경로>)      (새 판일 때만)
````

1층 `1-overview.md`:

````markdown
## 한 문장
## 개발 경험으로 보면      (선택)
## 그림
## 실제 코드
<단계 표: 단계 | 입력 | 출력 | 진입 파일:줄>
## 예외: 이 문서에서 뺀 것
<이름만 한 줄씩>
````

2층 `2-<…>.md`:

````markdown
<이 그림에서 볼 것 → 그림 → 근거 → 실제 코드 → 설명>
## 예외: 이 문서에서 뺀 것      (있을 때만)
````

3층 `3-<…>.md`:

````markdown
## 규칙
## 지금 어긋난 곳 / 문제 지점
<빨간 선으로 표시한 그림 → 근거 → 쓰는 자리>
````

- **1층 — 전체 큰 흐름**: 주제 전체를 한 그림에 놓는다. 예외는 뺀다. 1층만 읽어도 "무엇이 어떤 차례로 무엇을 넘기는가"가 서야 한다. 단계 표에 2층 파일이 있는 단계는 그 파일을 링크하지 않는다 — 1층은 고치지 않으므로, 링크는 대화의 [읽을 곳](#대화에-주는-읽을-곳)이 맡는다.
- **2층 — 세부 흐름**: 주제가 흐름이면 단계 하나, 흐름이 아니면 개념 하나를 한 파일에 쓴다. 개념이면 그 파일이 전제로 삼는 2층 파일을 머리의 함께 보는 파일에 적는다 — 전제 파일에서 안 다룬 말을 꺼내야 하면 개념을 쪼개야 한다는 뜻이다. 주제와 무관한 단계 안쪽은 "다루지 않는다"고 한 줄만 쓴다. 예외는 뺀다.
- **3층 — 결정에 걸린 것**: 그 결정을 고르는 데 꼭 필요한 규칙, 지금 상태, 문제 지점만 담는다. 1·2층을 읽었다고 전제하되, 그 전제가 되는 파일을 머리의 함께 보는 파일에 적는다. 결정이 예외 상황에서 갈리면 그 예외만 여기서 다룬다. 선택지 비교와 추천은 쓰지 않는다 — 그것은 묻는 스킬이 대화에서 한다.
- **예외**: 뺀 예외를 이름만 적는다. 사람이 "이것도 있구나"를 알게 하되 정상 흐름을 흐리지 않게 한다.

## 절 하나 쓰는 법

1. **이 그림에서 볼 것** — 그림 위에 한두 줄.
2. **그림** — 아래 [그림](#그림) 규칙.
3. **근거** — 그림 아래 `파일:줄` 링크. 문서나 코드에서 확인하지 못한 관계는 그리지 않는다.
4. **실제 코드** — 저장소의 실제 줄을 `파일:줄` 링크와 함께 그대로 인용한다. 한 줄로 뜻이 서지 않으면 서너 줄 토막까지 괜찮다. 인용 전에 그 줄을 실제로 읽어 줄 번호를 확인한다. 핵심이 코드가 아니라 문서의 규칙이면 그 문서의 한 줄을 인용한다. 알맞은 실제 줄이 없으면 짧은 의사코드를 쓰고 `의사코드 — 실제 코드 아님`이라고 표시한다.
5. **설명** — 코드 아래에 그 줄에서 무슨 일이 일어나는지, 그림과 어떻게 맞물리는지 쉬운 말로 쓴다.
6. **개발 경험으로 보면**(선택) — 읽는 사람이 이미 아는 개발 개념에 걸어 준다. 예: "단계 사이 약속은 npm 패키지의 `exports` 와 같다". 그림과 코드로 충분하면 넣지 않는다. 억지로 맞춘 예는 빼는 편이 낫다.

표 위에 붙는 작은 제목은 굵은 글씨 문단이 아니라 `####` 제목으로 쓴다. 굵은 글씨 문단은 위의 코드 블록·표에 바짝 붙어 읽기 어렵다.

## 그림

mermaid 로 그린다. 같은 개념을 다른 각도에서 보여야 이해가 서면 여러 종류를 쓴다.

| 보이려는 것 | mermaid 그림 |
|---|---|
| 단계·모듈 사이 흐름과 갈림길 | `flowchart` |
| 누가 누구를 어떤 차례로 부르나 | `sequenceDiagram` |
| 모듈·파일·타입 사이 관계와 의존 방향 | `flowchart`(subgraph 로 단계 묶기) 또는 `classDiagram` |
| 상태가 어떻게 바뀌나 | `stateDiagram-v2` |
| 데이터 모양과 관계 | `erDiagram` 또는 `classDiagram` |
| 바뀌기 전 / 후 | 같은 종류 그림 두 장(`전`, `후` 제목) |

- **문제 지점은 빨간색으로 표시한다.** 3층 파일에서 결정이나 질문이 걸린 선·상자를 한눈에 보이게 하려는 것이다. 선은 `linkStyle <선 차례> stroke:#d33,stroke-width:2px`, 상자는 `classDef problem stroke:#d33,stroke-width:2px` 와 `class <상자> problem`. 한 그림의 빨간 표시는 그 그림이 말하려는 한 곳에만 둔다.
- 내부 소스를 그릴 때는 상자에 **`파일 : 함수`** 를 적는다(예: `src/order/checkout.ts : placeOrder`). 적은 파일·함수는 실제로 있는지 확인한다.
- 언어·런타임의 일반 규칙(예: JavaScript 함수 스코프)은 그려도 되지만 `언어 규칙`이라고 밝힌다.
- mermaid 문법이 깨지지 않게 한다.
  - `flowchart`·`classDiagram` 상자 이름에 괄호·콜론·슬래시가 들어가면 따옴표로 감싼다(`A["src/order/checkout.ts : placeOrder"]`).
  - `sequenceDiagram` 참여자 별칭과 `stateDiagram-v2` 이름에서는 콜론·세미콜론이 문법을 깨므로 `파일 함수`처럼 공백으로 가른다(`participant CO as checkout.ts placeOrder`).
  - 문서를 다 쓰면 mermaid CLI(예: `npx -y @mermaid-js/mermaid-cli@11.4.0`)로 블록마다 그려 보아 문법 오류를 잡는다. 검사용 파일은 임시 폴더에 두고 끝나면 지운다. CLI 를 못 쓰면 눈으로 꼼꼼히 보고, 못 돌렸다는 사실을 부른 쪽에 알린다.

## 링크

- **문서 안**: 문서는 저장소 밖 임시 폴더에 있으므로, 저장소 파일과 다른 층 파일은 **`/` 로 시작하는 절대 경로**로 건다(`[checkout.ts:38-39](/home/me/repo/src/order/checkout.ts#L38-L39)`). 상대 경로는 열리지 않는다.
- **대화**: 저장소·작업 폴더 안 파일은 작업 폴더 기준 상대 경로, 그 밖 파일(층 파일 포함)은 절대 경로로 건다. 링크 글자는 파일 이름만 쓴다. `~`·`$TMPDIR` 같은 줄임 없이 실제 경로를 쓴다.

### 대화에 주는 읽을 곳

질문할 때마다 1층·2층·3층 세 줄을 같은 차례로 준다. 사람이 매번 같은 자리에서 링크를 찾고, 이미 본 것은 건너뛰게 하려는 것이다.

```markdown
읽을 곳:
- 1층 <풀어 쓴 이름> (<표시>): [1-overview.md](</로 시작하는 절대 경로>)
- 2층 <풀어 쓴 이름> (<표시>): [2-<…>.md](<…>)
- 3층 <풀어 쓴 이름> (<표시>, 빨간 선이 문제 지점): [3-<…>.md](<…>)
```

- 표시는 `새로`(이번에 처음 링크함), `앞과 같음`(앞서 링크한 그 파일), `새 판`(앞서 준 파일을 고친 판) 가운데 하나.
- 2층이 여럿에 걸리면 2층 줄에 링크를 여럿 준다.
- 3층 파일이 없으면 `- 3층: 없음` 으로 쓴다.

## 지킬 것

- **이름을 번호나 약칭으로만 부르지 않는다.** "후보 3", "D6", "§2" 처럼 정의를 알아야 뜻이 통하는 이름만 쓰지 않는다. 근거 문서가 그렇게 불러도 내용이 드러나는 짧은 이름을 지어 쓴다.
- **문서에 없는 사실을 만들지 않는다.** 코드·문서에서 확인한 것만 쓴다. 확인 못 한 것은 "확인하지 못했다"고 쓴다.
- **수치를 쓰면 출처를 붙인다.** 직접 잰 수치에는 그 수치를 낸 명령을, 문서에서 옮긴 수치에는 그 문서의 `파일:줄` 을 붙인다. 실행하지 않은 명령의 수치는 쓰지 않는다.
- **근거 문서와 코드는 읽기만 한다.** 고칠 거리를 발견해도 고치지 않고 부른 쪽에 알리기만 한다. 쓰는 파일은 이해 문서 폴더의 층 파일뿐이다.

## 부른 쪽에 넘기는 것

- 이해 문서 폴더의 절대 경로.
- 이번 [읽을 곳](#대화에-주는-읽을-곳) 블록(표시까지 채운 것).
- 새로 만든 파일과 새 판을 만든 파일, 새 판이면 그 까닭.
- 문서와 코드가 달랐던 곳, 문법 검사를 못 돌렸으면 그 사실.

대화에는 문서 내용을 옮겨 적지 않는다. 대화는 읽을 곳 블록과 질문만 갖는다.
